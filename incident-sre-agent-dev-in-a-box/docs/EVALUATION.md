# Incident SRE Agent — Scenario Evaluation Scorecard & Engineering Backlog

This document records the official, un-tuned, and honest evaluation of the de-overfitted Incident SRE Agent across all 5 demonstration failure scenarios against Google Cloud Run in a live Google Cloud environment, comparing the Initial Baseline with the Agentic Specialists Refactoring (Current Release), followed by the comprehensive engineering backlog.

---

## 1. Evaluation Methodology

Investigations were evaluated using strict operational guidelines to ensure realistic, unassisted telemetry reasoning:
- **Symptom-Only Incident Tickets**: Webhooks and ticket payloads contained exclusively customer-facing symptoms (e.g., HTTP 500 error rates, latency spikes, or broken checkouts) with zero scenario numbers, service architecture hints, or root cause clues matching `demo/SCENARIOS.md`.
- **5-Minute Stabilization Window**: Following fault injection, each scenario ran under continuous background traffic (`loadgen.py` at 0.5 rps) for $\ge 5$ minutes before ticket creation. This guaranteed that Cloud Run request metrics, container instance scaling, and Google Cloud Error Reporting groups ingested and aggregated realistically.
- **Strict Baseline Isolation (Current Release)**: To eliminate rolling lookback window bleed and cross-scenario contamination (which affected the Initial Baseline), the Current Release enforced a strict $\ge 60$ minutes clean baseline (100% 200 OK traffic under continuous 0.5 rps loadgen) between every scenario.
- **100% Model-Authored Analysis**: Post-LLM template overrides were completely eliminated and barred by AST syntax guards (`scripts/check-no-rootcause-overrides.py`). All summaries, probable root causes, timelines, and confidence scores were authentically generated by Gemini on Vertex AI.
- **Progressive Skill Loading (Current Release)**: Each specialist was refactored into an independent ADK `LlmAgent` endowed with its own domain `SkillToolset`. Domain playbooks (`cloud-logging-queries`, `cloud-monitoring-metrics`, `change-correlation`, `cloud-run-troubleshooting`) were progressively loaded, enabling `skill_first=True` tool discovery without polluting top-level prompt context.

## 6. Prioritized Engineering Backlog

The following 12 backlog items detail concrete engineering improvements identified during live evaluations. Each item includes problem analysis and proposed technical specifications.

### Item 1: Structured JSON Application Logging in Demo Services (`severity` field for Cloud Run)
- **Status**: Implemented in demo services; Cloud Run log driver surfaces structured JSON payloads.
- **Problem**: Python applications logging plain text to stderr (`sys.stderr`) cause Cloud Run's log driver to classify entries as `DEFAULT` severity. Because `LogsSpecialist` queries Cloud Logging using `severity >= WARNING`, genuine application error logs were excluded from query results in the initial baseline.
- **Specification**: In `demo/shop-api/shop_app.py` and `demo/inventory-svc/inventory_app.py`, configure a JSON log formatter outputting structured log payloads containing `"severity": "ERROR"`, `"message": "..."`, and `"serviceContext": {"service": ...}`. This enables Google Cloud Logging native severity filtering to surface application errors immediately.

### Item 2: Querying Request Logs by HTTP Status (4xx/5xx) in `LogsSpecialist`
- **Status**: Implemented in `LogsSpecialist` recipe and skill playbook.
- **Problem**: When application container logs are unstructured or suppressed, the Cloud Run request log (`logName =~ "run.googleapis.com%2Frequests"`) retains authoritative HTTP status codes in `httpRequest.status`.
- **Specification**: Extend `LogsSpecialist` filter recipes to include `(httpRequest.status >= 500 OR httpRequest.status = 403)` when querying Cloud Run services, ensuring HTTP-level failures are detected regardless of application log formatting.

### Item 3: Downstream Dependency Traversal & Distributed Graph Scoping
- **Status**: Planned.
- **Problem**: In Scenario 2 and Scenario 5, when primary services exhibit latency stalls or 502 errors, the agent must trace outbound dependencies across service boundaries.
- **Specification**: In `Triage` and `ResourcesSpecialist`, parse service environment variables (`INVENTORY_SERVICE_URL`) and infrastructure mappings to discover downstream dependency targets. When 502 Bad Gateway or 504 Gateway Timeout errors occur on the primary service, automatically fan out secondary telemetry queries across downstream services.

### Item 4: Temporal Disambiguation of Resolved vs. Ongoing Error Signals
- **Status**: Partially mitigated by 60-min baseline isolation; automated in-agent filter planned.
- **Problem**: When incidents occur within 60 minutes of prior resolved faults, residual error groups from Google Cloud Error Reporting and 15-minute rolling metric windows remain active in the lookback window.
- **Specification**: Enhance `Synthesizer` and `MetricsSpecialist` to evaluate signal lifecycles. If an error group's last seen timestamp or metric spike ended before a clear recovery preceding the current incident symptom onset, the synthesizer must isolate it as a resolved prior event rather than the causal driver of the current ongoing incident.

### Item 5: Temporal Revision-Causality Guard
- **Status**: Planned.
- **Problem**: In Scenario 4, the root cause narrative attributed runtime OOM saturation to a revision deployed hours earlier.
- **Specification**: Implement a temporal causality constraint in `ChangesSpecialist` and `Synthesizer`: a deployment or configuration revision may only be declared the primary causal mechanism if its deployment timestamp falls within or immediately preceding the symptom onset window (e.g. within 30–60 minutes of ticket creation). Historical revisions deployed hours or days earlier must be classified as ambient baselines.

### Item 6: Symptom-Mismatch Confidence Down-Calibration
- **Status**: Implemented in Synthesizer.
- **Problem**: When deduced root causes contradict the symptoms reported in the incident ticket, confidence scoring can remain deceptively high.
- **Specification**: In `agent/app/synthesizer.py`, enforce an automated confidence cap ($\le 0.50$) whenever the primary HTTP status codes in telemetry directly conflict with the reported ticket symptoms, accompanied by an explicit caveat highlighting the discrepancy.

### Item 7: Specialists Loading Domain Skills in Reporting
- **Status**: **COMPLETED**.
- **Resolution**: Refactored `LogsSpecialist`, `MetricsSpecialist`, `ChangesSpecialist`, and `ResourcesSpecialist` into independent ADK `LlmAgent` instances initialized with `SkillToolset` loading their respective domain playbooks. Verified `skill_first=True` across 100% of specialists and confirmed all domain skills appear dynamically in `skills_used`.

### Item 8: Configurable Deduplication TTL & Distributed Store (Redis / Firestore)
- **Status**: Planned for production hardening.
- **Problem**: `CallbackDedupRegistry` currently uses a hardcoded in-memory TTL dictionary (600.0s) inside the `incident-bridge` process. When Cloud Run scales to multiple container instances (`max_instance_count > 1`), an agent retry routed to a different bridge instance would bypass the in-memory cache.
- **Specification**: Externalize TTL via configuration (`BRIDGE_CALLBACK_DEDUP_TTL_SECONDS`) and implement a pluggable storage interface in `bridge/app/core/dedup.py` supporting Google Cloud Memorystore (Redis) or Firestore for distributed, multi-instance deduplication.

### Item 9: Real Revision and IAM Fault Injection for Scenarios 3 and 5
- **Status**: Planned for end-to-end chaos testing.
- **Problem**: Scenarios 3 (Bad Release) and 5 (Dependency Failure) currently utilize in-app fault injection switches in `shop-api` rather than authentic cloud infrastructure mutations.
- **Specification**: Implement real cloud infrastructure fault injection scripts:
  - Scenario 3: Deploy an actual Cloud Run revision with a missing environment variable or bad readiness probe (`gcloud run deploy --update-env-vars PAYMENT_GATEWAY_KEY=""`).
  - Scenario 5: Remove the actual IAM invoker binding on `inventory-svc` (`gcloud run services remove-iam-policy-binding inventory-svc --member="serviceAccount:shop-api-sa@..." --role="roles/run.invoker"`).

### Item 10: Consolidating Legacy Historical Logs into Clean Documentation
- **Status**: **COMPLETED**.
- **Resolution**: Consolidated and archived historical documentation into canonical guides in `docs/` (`docs/ARCHITECTURE.md`, `docs/DESIGN.md`, `docs/EVALUATION.md`, `docs/OPERATIONS.md`, `docs/SECURITY.md`, `docs/TESTING.md`).

### Item 11: Inventory Stock Replenishment Under Sustained Traffic (HTTP 409)
- **Status**: **COMPLETED**.
- **Resolution**: Authenticated inventory restock endpoint (`POST /inventory/restock`) added to `inventory-svc` and invoked prior to each scenario execution during automated evaluation runs.

### Item 12: Revision Boundary Partitioning in Log Lookback Windows
- **Status**: Planned.
- **Problem**: When a new revision deployment occurs within the lookback window, errors unique to superseded revisions may pollute the impact statement of the current active revision.
- **Specification**: Partition log streams by revision and prevent errors unique to superseded revisions from polluting the impact statement of the current active revision.

### Item 13: Metrics Tool-Argument Format Normalization (`status_code_range`)
- **Status**: Identified during live evaluation.
- **Problem**: In Scenarios 1 and 5, `MetricsSpecialist` passed wildcard parameter `'5xx'` to `query_time_series`, raising `Invalid status_code_range '5xx'. Expected 3-digit HTTP code (e.g. '500') or range (e.g. '500-599')`. While the specialist recovered via `compare_to_baseline`, the tool schema should natively parse wildcard status classes.
- **Specification**: Update `agent/app/tools/monitoring.py` to parse `'5xx'`, `'4xx'`, `'2xx'` into corresponding numeric ranges `500-599`, `400-499`, `200-299`.

## 7. Known Limitations

1. **Downstream Span Visibility**: Without distributed tracing (Google Cloud Trace), delays occurring inside third-party synchronous endpoints or internal handler sleep functions cannot be distinguished at the millisecond span level without inference (Backlog Item 3).
2. **Status Code Class Wildcards in Metrics Tool**: Metrics tool parameter `status_code_range` currently expects numeric ranges (e.g. `500-599`) rather than wildcard notation (e.g. `5xx`), which triggers parameter validation errors requiring fallback to baseline comparison (Backlog Item 13).
3. **In-Memory Callback Deduplication**: Multi-instance deployments require Redis/Firestore backend per Backlog Item 8.
4. **Log Format Severity Sensitivity**: Unstructured logs on Cloud Run default to `DEFAULT` severity and are ignored by `severity >= WARNING` filters; JSON logging is required per Backlog Item 1.
5. **Synthesizer Field Regeneration**: In Scenario 4, the initial synthesis pass omitted the root-cause field, requiring an automatic secondary LLM pass to complete the report structure.
6. **Revision-Causality Attribution Overreach**: In Scenario 4, the root cause narrative attributed container restart to the rollout of revision `00003-zqr` deployed hours prior (hedged by 0.5 confidence; to be addressed in timeline correlation).
7. **Test-Method Boundary Conditions**: Scenarios 3 and 5 utilize in-app fault injection switches rather than live IAM/deployment mutations; Scenario 1 had an ~11-minute active traffic baseline following loadgen restart (while Scenarios 4, 2, 3, and 5 enforced full $\ge 60$-minute baselines).
