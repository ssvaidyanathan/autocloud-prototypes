# Incident SRE Agent — Scenario Evaluation Scorecard & Engineering Backlog

This document records the official, un-tuned, and honest evaluation of the de-overfitted Incident SRE Agent across all 5 demonstration failure scenarios against Google Cloud Run in a live Google Cloud environment, followed by the comprehensive engineering backlog.

---

## 1. Evaluation Methodology

Investigations were evaluated using strict operational guidelines to ensure realistic, unassisted telemetry reasoning:
- **Symptom-Only Incident Tickets**: Webhooks and ticket payloads contained exclusively customer-facing symptoms (e.g., HTTP 500 error rates, latency spikes, or broken checkouts) with zero scenario numbers, service architecture hints, or root cause clues.
- **5-Minute Stabilization Window**: Following fault injection, each scenario ran under continuous background traffic (`loadgen.py`) for $\ge 5$ minutes before ticket creation. This guaranteed that Cloud Run request metrics, container instance scaling, and Google Cloud Error Reporting groups ingested and aggregated realistically.
- **Lookback Overlap Caveat**: Scenarios were executed sequentially in a single environment. Because the agent queries rolling 15-to-60-minute lookback windows, telemetry occasionally contained residual error signatures, log entries, or metric excursions from preceding scenarios. This surfaced real-world multi-incident disambiguation challenges recorded honestly below.
- **100% Model-Authored Analysis**: Post-LLM template overrides were completely eliminated and barred by AST syntax guards (`scripts/check-no-rootcause-overrides.py`). All summaries, probable root causes, timelines, and confidence scores were authentically generated by Gemini on Vertex AI.

## 3. Scorecard Summary & Key Findings

- **Scenario 1 (Error Spike)**: **PASS** across both ServiceNow and Jira Cloud. Grounded identification of database connection pool exhaustion in asyncpg on `/checkout` with verified zero duplicate postings.
- **Scenario 2 (Latency Spike)**: **PARTIAL [Overlap]** across both ServiceNow and Jira Cloud. Accurately captured the massive latency surge (+66,108%, 98.7s p95), but attributed the root cause mechanism to residual Scenario 1 database pool errors in the overlapping lookback window.
- **Scenario 3 (Bad Release)**: **PARTIAL [Symptoms Correct, Mechanism Missed]** across both ServiceNow and Jira Cloud. Correctly identified 503s on `/readyz` and `/checkout`, but failed to extract the missing `PAYMENT_GATEWAY_KEY` configuration string and attributed causation to a historical revision deployed >11h prior.
- **Scenario 4 (Memory Leak)**: **PASS (mechanism) with grounding error** across both ServiceNow and Jira Cloud. Diagnosed container memory saturation (1043 MiB vs 1024 MiB limit) and OOM container crash from Cloud Run infrastructure logs. Impact narrative included unsupported 404 claims ingested from pre-fix warning logs on the prior revision.
- **Scenario 5 (Dependency Failure)**: **FAIL / PARTIAL [Lookback Overlap & Log Severity Filter]** across both ServiceNow and Jira Cloud. Captured downstream 502 Bad Gateway symptoms, but misattributed root cause to residual Scenario 4 OOM crashes because plain-text stderr logs received `DEFAULT` Cloud Run severity (filtered out by `severity >= WARNING`) and the agent's query scope was restricted to the primary CI (`acme-shop-api`), omitting downstream `acme-inventory-svc`.

## 4. Prioritized Engineering Backlog

The following 12 backlog items detail concrete engineering improvements identified during live evaluation. Each item includes problem analysis and proposed technical specifications.

### Item 1: Structured JSON Application Logging in Demo Services (`severity` field for Cloud Run)
- **Problem**: Python applications logging plain text to stderr (`sys.stderr`) cause Cloud Run's log driver to classify entries as `DEFAULT` severity. Because `LogsSpecialist` queries Cloud Logging using `severity >= WARNING`, genuine application error logs (such as `[ERROR] shop-api: Downstream dependency inventory-svc returned HTTP 403 Forbidden`) are excluded from query results.
- **Specification**: In `demo/shop-api/shop_app.py` and `demo/inventory-svc/inventory_app.py`, configure a JSON log formatter outputting structured log payloads containing `"severity": "ERROR"`, `"message": "..."`, and `"serviceContext": {"service": ...}`. This enables Google Cloud Logging native severity filtering to surface application errors immediately.

### Item 2: Querying Request Logs by HTTP Status (4xx/5xx) in `LogsSpecialist`
- **Problem**: When application container logs are unstructured or suppressed, the Cloud Run request log (`logName =~ "run.googleapis.com%2Frequests"`) retains authoritative HTTP status codes in `httpRequest.status`. However, `LogsSpecialist` primarily filtered by log entry severity rather than explicitly querying `httpRequest.status >= 400`.
- **Specification**: Extend `LogsSpecialist` filter recipes to include `(httpRequest.status >= 500 OR httpRequest.status = 403)` when querying Cloud Run services, ensuring HTTP-level failures are detected regardless of application log formatting.

### Item 3: Downstream Dependency Traversal & Distributed Graph Scoping
- **Problem**: In Scenario 5, the agent scoped its telemetry queries strictly to the primary CI (`acme-shop-api`). The actual 403 Forbidden request logs and IAM permission failures occurred on the downstream dependency `acme-inventory-svc`, which was never queried.
- **Specification**: In `Triage` and `ResourcesSpecialist`, parse service environment variables (`INVENTORY_SERVICE_URL`) and infrastructure mappings to discover downstream dependency targets. When 502 Bad Gateway or 504 Gateway Timeout errors occur on the primary service, automatically fan out secondary telemetry queries across downstream services.

### Item 4: Temporal Disambiguation of Resolved vs. Ongoing Error Signals
- **Problem**: When incidents occur within 60 minutes of prior resolved faults, residual error groups from Google Cloud Error Reporting and 15-minute rolling metric windows remain active in the lookback window. In Scenario 2, the agent correctly identified the latency surge (+66,108%) but attributed it to residual Scenario 1 DB pool errors.
- **Specification**: Enhance `Synthesizer` and `MetricsSpecialist` to evaluate signal lifecycles. If an error group's last seen timestamp or metric spike ended before a clear recovery preceding the current incident symptom onset, the synthesizer must isolate it as a resolved prior event rather than the causal driver of the current ongoing incident.

### Item 5: Temporal Revision-Causality Guard
- **Problem**: In Scenario 3, the agent attributed incident causality to Cloud Run revision `acme-shop-api-00001-84p`, which had been deployed >11 hours prior, despite the incident symptoms appearing suddenly minutes before ticket filing.
- **Specification**: Implement a temporal causality constraint in `ChangesSpecialist` and `Synthesizer`: a deployment or configuration revision may only be declared the primary causal mechanism if its deployment timestamp falls within or immediately preceding the symptom onset window (e.g. within 30–60 minutes of ticket creation). Historical revisions deployed hours or days earlier must be classified as ambient baselines.

### Item 6: Symptom-Mismatch Confidence Down-Calibration
- **Problem**: When deduced root causes contradict the symptoms reported in the incident ticket (e.g., ticket reports HTTP 503, but telemetry only demonstrates HTTP 500), confidence scoring can remain deceptively high.
- **Specification**: In `agent/app/synthesizer.py`, enforce an automated confidence cap ($\le 0.50$) whenever the primary HTTP status codes in telemetry directly conflict with the reported ticket symptoms, accompanied by an explicit caveat highlighting the discrepancy.

### Item 7: Specialists Loading Domain Skills in Reporting
- **Problem**: While the top-level Dispatcher loads `triage-playbook` and Synthesizer loads `report-style`, domain specialists (`Logs`, `Metrics`, `Changes`, `Resources`) execute read-only tools directly without invoking sub-agent Skill toolsets. Consequently, domain skills (`cloud-logging-queries`, `cloud-monitoring-metrics`, `change-correlation`) do not appear in the reported `skills_used` list.
- **Specification**: Refactor specialist sub-agents in `agent/app/specialists/` to initialize with ADK `SkillToolset` loading their respective domain playbooks, allowing dynamic skill tracking to capture domain skills across all execution phases.

### Item 8: Configurable Deduplication TTL & Distributed Store (Redis / Firestore)
- **Problem**: `CallbackDedupRegistry` currently uses a hardcoded in-memory TTL dictionary (600.0s) inside the `incident-bridge` process. When Cloud Run scales to multiple container instances (`max_instance_count > 1`), an agent retry routed to a different bridge instance would bypass the in-memory cache.
- **Specification**: Externalize TTL via configuration (`BRIDGE_CALLBACK_DEDUP_TTL_SECONDS`) and implement a pluggable storage interface in `bridge/app/core/dedup.py` supporting Google Cloud Memorystore (Redis) or Firestore for distributed, multi-instance deduplication.

### Item 9: Real Revision and IAM Fault Injection for Scenarios 3 and 5
- **Problem**: Scenarios 3 (Bad Release) and 5 (Dependency Failure) currently utilize in-app fault injection switches in `shop-api` rather than authentic cloud infrastructure mutations.
- **Specification**: Implement real cloud infrastructure fault injection scripts:
  - Scenario 3: Deploy an actual Cloud Run revision with a missing environment variable or bad readiness probe (`gcloud run deploy --update-env-vars PAYMENT_GATEWAY_KEY=""`).
  - Scenario 5: Remove the actual IAM invoker binding on `inventory-svc` (`gcloud run services remove-iam-policy-binding inventory-svc --member="serviceAccount:shop-api-sa@..." --role="roles/run.invoker"`).

### Item 10: Consolidating Legacy Historical Logs into Clean Documentation
- **Problem**: Project history was split between historical design logs in early development branches and canonical documentation in `docs/`.
- **Specification**: Consolidate and archive historical documentation into structured guides in `docs/` (`docs/ARCHITECTURE.md`, `docs/DESIGN.md`, `docs/EVALUATION.md`, `docs/OPERATIONS.md`, `docs/SECURITY.md`, `docs/TESTING.md`) and remove obsolete scratch files from release artifacts.

### Item 11: Inventory Stock Replenishment Under Sustained Traffic (HTTP 409)
- **Finding**: Under sustained continuous load generation (~4.5–5 req/s), checkout requests on `/checkout` periodically return HTTP 409 Conflict originating from `inventory-svc`'s `/inventory/reserve` endpoint.
- **Root Cause**: The demo `inventory-svc` tracks finite stock quantities per item (initialized between 5 and 100 units). When `loadgen.py` continuously purchases items, stock for individual items is depleted to 0, causing genuine business-logic reservation rejections (HTTP 409 Conflict). While not an infrastructure or application defect, this introduced baseline 409 noise into telemetry windows.
- **Backlog Specification**:
  1. Update `demo/scripts/reset.sh` to explicitly invoke an inventory restock endpoint (`POST /inventory/restock`) or reset inventory quantities to default levels upon baseline restoration.
  2. Alternatively, configure a steady stock replenishment loop in `inventory-svc` during demo mode to ensure continuous loadgen testing maintains non-zero inventory buffers.

### Item 12: Revision Boundary Partitioning in Log Lookback Windows
- **Problem**: In Scenario 4, the agent cited HTTP 404 errors in its impact statement that were emitted by a previous revision before the baseline revision was rolled out, because the 15-minute investigation window crossed the revision deployment boundary.
- **Specification**: When a new revision deployment occurs within the lookback window, partition log streams by revision and prevent errors unique to superseded revisions from polluting the impact statement of the current active revision.

## 5. Known Limitations

1. **Single-Service Focus**: Telemetry gathering currently prioritizes the primary service named in ticket metadata or inferred from logs; multi-tier downstream trace correlation requires implementation of Backlog Item 3.
2. **Rolling Window Telemetry Bleed**: Rapid consecutive scenario tests share rolling telemetry windows; resolved error groups and metric spikes may still be cited unless filtered per Backlog Items 4 and 12.
3. **In-Memory Callback Deduplication**: Multi-instance deployments require Redis/Firestore backend per Backlog Item 8.
4. **Log Format Severity Sensitivity**: Unstructured logs on Cloud Run default to `DEFAULT` severity and are ignored by `severity >= WARNING` filters; JSON logging is required per Backlog Item 1.
